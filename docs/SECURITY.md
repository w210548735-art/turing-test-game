# Security Policy

## Supported version

安全修复只维护默认分支的最新版本。部署方应及时更新依赖、运行数据库迁移，
并在发布前完成备份与恢复验证。

## Reporting a vulnerability

请通过 GitHub 的私密漏洞报告功能联系维护者。不要在公开 Issue、讨论区、
提交信息或日志中发布漏洞利用细节、用户数据、服务器地址或任何凭据。

报告应包含受影响版本、复现条件、影响范围和建议修复方向，但必须使用脱敏
样本。维护者确认前请勿公开披露。

## Secret handling

生产 Secret 只能通过环境变量、容器 Secret 或受权限保护的文件注入。仓库
仅提供占位示例，任何真实密码、Token、邮箱授权码、私钥和数据库备份都不得
进入 Git。

## Email verification

- 注册和重新发送验证邮件使用不可枚举的统一公共响应；
- 仅 `PENDING_EMAIL` 账户会触发重发，已激活或不存在的邮箱不会泄露状态；
- 每次注册重试、验证邮件重发和密码恢复都会原子轮换同账户、同用途的未使用
  Token，旧链接立即失效；
- 重发与首次验证邮件共用复合限流，限制单邮箱、来源地址、设备与全局流量；
- 邮件中的原始 Token 只交给投递适配器，不写入账户记录、日志或告警。

## SMTP delivery alerts

SMTP 投递失败不会改变注册、验证邮件重发或密码恢复的公共成功响应，以免构成
账号存在性旁路。服务会记录错误级结构化事件 `SMTP_DELIVERY_FAILED`，字段仅
包含邮件用途、业务操作、错误类型、发生时间与聚合失败计数，不包含邮箱、Token、
密码、授权码或底层错误正文。

服务内 `smtpDelivery` 快照记录 `ok/degraded`、连续失败、累计失败和最近失败
时间，成功投递后连续失败数恢复为零。公共 `/api/health` 与 `/api/ready`
不得暴露这些计数，否则攻击者可结合重发请求建立账户枚举旁路。部署方应将错误级
结构化日志或 `onSmtpDeliveryAlert` 回调接入受控监控通知渠道。
